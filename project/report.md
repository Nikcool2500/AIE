# 2. Постановка задачи и контекст

## 1. Предметная область и задача

**Предметная область:** Финансовые услуги / кредитный скоринг.

**Задача:** Прогнозирование кредитного лимита для клиента на основе его демографических характеристик, финансовой истории и поведения при использовании банковских продуктов.

**Тип задачи:** Регрессия (предсказание непрерывной числовой величины — кредитного лимита).

**Потенциальный пользователь сервиса:**
- **Кредитный аналитик / риск-менеджер** банка, который использует модель для предварительной оценки допустимого кредитного лимита при рассмотрении заявок.
- **Сценарий использования:** При поступлении заявки от клиента система автоматически рассчитывает рекомендованный кредитный лимит на основе профиля клиента. Это позволяет ускорить процесс принятия решений, снизить субъективность оценки и минимизировать риски выдачи чрезмерных лимитов.

## 2. Формулировка задачи в терминах ML/ИИ

**Входные данные (признаки):**

| Требование | Обоснование |
|------------|-------------|
| **Интерпретируемость** | Важно для риск-менеджеров: необходимо понимать, какие факторы влияют на прогноз лимита |
| **Качество прогноза** | Достаточно высокий R² и низкий RMSE для практической применимости |

## 3. Целевые метрики качества

**Основные метрики для оценки модели:**

- **RMSE**
- **MAE**
- **R²**
- **MSE**

**Почему выбраны именно эти метрики:**
1. **RMSE + MAE** дают комплексное представление: RMSE акцентирует внимание на критических ошибках, MAE — на типичном отклонении.
2. **R²** позволяет быстро оценить, насколько модель лучше простого среднего (базлайна).
3. Все метрики стандартны для задач регрессии, легко интерпретируются бизнес-пользователями и поддерживаются в `sklearn`.

## 3. Предобработка и EDA

### Основные шаги предобработки

1. **Очистка данных**:
   - Удаление служебных колонок (`CLIENTNUM`, `Unnamed: 19`)
   - Фильтрация аномалий: `Customer_Age <= 80`

2. **Обработка пропусков**:
   - Категориальные признаки: заполнение значением `'Unknown'`
   - Числовые признаки: заполнение медианой

3. **Кодирование категориальных признаков**:
   - `TargetEncoder` с обработкой неизвестных категорий (handle_unknown='value') и сглаживанием (smoothing=10.0)

4. **Масштабирование числовых признаков**:
   - `StandardScaler` — приводит признаки к стандартному нормальному распределению

5. **Логарифмирование признаков с длинным хвостом**:
   - Признаки с сильной правосторонней асимметрией (например, `Total_Revolving_Bal`, `Total_Trans_Amt`) были логарифмированы: `np.log1p(x)`. Это улучшило нормальность распределения и качество предсказаний модели

6. **Разделение данных**:
   - Train/Validation/Test в пропорции ~60/20/20 с фиксированным `random_state=42`

### Важные наблюдения из EDA

- **Распределения**: многие числовые признаки имеют скошенное распределение с длинным правым хвостом
- **Пропуски**: незначительные, равномерно распределены → заполнение медианой/модой не вносит сильного смещения

## 4. Модели и эксперименты

### 1. Базовые (baseline) модели
Развитие подхода началось с линейной модели для оценки линейной разделимости задачи и MLP-бейзлайна для оценки потенциала нелинейных зависимостей.

- **Linear Regression** (`notebooks/lin-reg-eda-base.ipynb`)
  - **Подход**: Линейная регрессия на признаках после `TargetEncoder` (`smoothing=10.0`) и `RobustScaler`. 
  - **Результаты**: `R² ≈ 0.634`, `RMSE ≈ 5446`, `MAE ≈ 4006` на тестовой выборке. 5-Fold кросс-валидация подтвердила стабильность (`R² = 0.634`) и отсутствие переобучения. Модель выступила нижней границей качества, показав, что задача требует нелинейного моделирования.

- **Neural Network (MLP Baseline)** (`notebooks/nn-base.ipynb`)
  - **Подход**: Двухслойный перцептрон (64→64 нейронов, ReLU) с оптимизатором `Adam` (`lr=1e-3`) и функцией потерь `MSELoss`.
  - **Результаты**: Качественный скачок относительно линейки: `R² ≈ 0.883`, `RMSE ≈ 3108`, `MAE ≈ 1482` на тесте. Продемонстрировала способность архитектуры захватывать сложные взаимодействия признаков без явного фич-инжиниринга.

### 2. Улучшенные модели и эксперименты
После получения первых бейзлайнов фокус сместился на работу с распределениями признаков, регуляризацию и автоматический подбор гиперпараметров.

- **Логарифмирование признаков и таргета** (`notebooks/nn-base-with-log.ipynb`)
  - **Эксперимент**: Применение `np.log1p()` к признакам с тяжёлым правым хвостом (`Total_Revolving_Bal`, `Total_Trans_Amt`, `Total_Amt_Chng_Q4_Q1` и др.) и тестовое логарифмирование целевой переменной.
  - **Влияние**: Сжатие хвостов распределений стабилизировало градиенты и уменьшило разрыв между train/val метриками. Тестовый `MAE` снизился до `~1317`, `R²` вырос до `0.893`. В итоговом пайплайне оставлено логарифмирование только признаков для сохранения интерпретируемости предсказаний в исходных денежных единицах.

- **Random Forest + Optuna** (`notebooks/random-forest.ipynb`)
  - **Подход**: Ансамбль деревьев с поиском гиперпараметров через Optuna (200 trials).
  - **Важные настройки**: `n_estimators=1050`, `max_depth=10`, `min_samples_leaf=5`. Ограничение глубины и увеличение минимального числа объектов в листе критически подавили переобучение на тренировочной выборке (Train `R²` снизился с 0.97 до 0.91, Test остался стабильным).
  - **Результаты**: `R² ≈ 0.886`, `RMSE ≈ 3071`, `MAE ≈ 1266` на тесте. Наименьшая абсолютная ошибка среди всех моделей.

- **CatBoost + Optuna** (`notebooks/catboost.ipynb`)
  - **Подход**: Градиентный бустинг с нативной обработкой категорий и оптимизацией (100 trials).
  - **Важные настройки**: `iterations=600`, `depth=8`, `learning_rate=0.0543`, `l2_leaf_reg=4.50`, `grow_policy='Lossguide'`. Регуляризация `l2_leaf_reg` и асимметричная политика роста дерева обеспечили лучший баланс bias-variance.
  - **Результаты**: Тестовые метрики: `R² ≈ 0.893`, `RMSE ≈ 2973`, `MAE ≈ 1335`. Показала наименьшую дисперсию ошибок и высокую устойчивость к шуму в признаках.

### 3. Нейросетевые модели (детали реализации)
- **Архитектура**: `nn.Sequential(Linear(17, 64) → ReLU → Linear(64, 64) → ReLU → Linear(64, 1))`. От использования `BatchNorm` отказались: эксперименты показали, что при текущем объёме данных он ускорял сходимость на train, но усиливал переобучение на validation.
- **Особенности обучения**:
  - **Оптимизатор**: `Adam` с фиксированным `lr=1e-3`. Scheduler не применялся, так как ранняя остановка эффективно контролировала переобучение.
  - **Размер батча**: `256`. Выбран эмпирически: меньшие батчи давали шумные градиенты, большие — замедляли выход на плато.
  - **Ранняя остановка**: `EarlyStopping(patience=150, min_delta=1e-7)`. Сработала на ~1250 эпохе из 7500, сохранив веса с лучшим validation loss.
  - **Воспроизводимость**: Полная фиксация сидов (`SEED=42`), `torch.backends.cudnn.deterministic=True`, контроль `PYTHONHASHSEED`.
  - **Трекинг**: Все запуски логировались в MLflow (`notebooks/mlruns/`). Фиксировались конфигурации, хеши данных, метрики по splits и артефакты моделей, что позволило провести честное сравнение подходов.

Ноутбуки: `lin-reg-eda-base.ipynb`, `nn-base.ipynb`, `nn-base-with-log.ipynb`, `random-forest.ipynb`, `catboost.ipynb`.

## 5. Экспериментальный протокол и результаты

### 1. Экспериментальный протокол
- **Разделение выборки:** Данные разделены на train/val/test в пропорции `60/20/20` с фиксированным `random_state=42`. Валидационная выборка использовалась для подбора гиперпараметров (Optuna) и контроля переобучения. Тестовая выборка изолирована на всех этапах обучения и применялась только для финальной оценки.
- **Расчёт метрик:** Метрики `R²`, `RMSE`, `MSE` и `MAE` вычислялись с помощью `sklearn.metrics` на отложенной `test`-выборке после сериализации финальных моделей. Все преобразования (кодирование, масштабирование, логарифмирование) применялись строго через `fit` на train и `transform` на val/test, что исключает data leakage.
- **Воспроизводимость:** Зафиксированы все сиды (`SEED=42`), порядок загрузки данных, хеш датасета (`md5`) и версии библиотек.

### 2. Сравнение моделей по метрикам
| Модель / конфигурация | Описание | R² (Test) | RMSE (Test) | MAE (Test) | Комментарий |
|-----------------------|----------|-----------|-------------|------------|-------------|
| **Linear Regression** | Линейная регрессия + TargetEncoder + StandardScaler | 0.636 | 5 440 | 3 827 | Стартовая точка: показывает наличие линейного сигнала, но недостаточно для задачи |
| **Neural Network (MLP)** | 2 скрытых слоя (64→64), Adam, EarlyStopping | 0.883 | 3 108 | 1 482 | Значительный прирост качества за счёт нелинейности, но требует масштабирования и дольше обучается |
| **NN + Log-features** | Та же архитектура + логарифмирование хвостовых признаков | 0.893 | 2 967 | 1 317 | Лучший результат среди нейросетей, лог-преобразование стабилизировало градиенты |
| **Random Forest (Optuna)** | 200 trials, `max_depth=10`, `min_samples_leaf=5` | 0.886 | 3 066 | 1 227 | Высокая точность, лучшая MAE, устойчив к шуму, но требует масштабирования |
| **CatBoost (Optuna)** | 100 trials, `depth=8`, `lr=0.054`, `l2_leaf_reg=4.50` | 0.893 | 2 973 | 1 335 | Нативная работа с категориями, встроенная регуляризация, стабильные метрики |

### 3. Выбор финальной модели
**Финальная модель:** `CatBoostRegressor` (ансамбль деревьев с градиентным бустингом).

**Обоснование выбора:**
1. **Интерпретируемость для бизнеса:** В кредитном скоринге важно понимать, какие факторы влияют на лимит. CatBoost предоставляет встроенную важность признаков (`feature_importances_`) и полностью совместим с SHAP/LIME, что позволяет формировать объяснимые отчёты для аналитиков и регуляторов.
2. **Высокая точность:** Метрики на тесте сопоставимы с лучшей нейросетью (R² ≈ 0.893, RMSE ≈ 2 973).
3. **Устойчивость к предобработке:** Модель менее чувствительна к масштабированию и выбросам по сравнению с линейными моделями и MLP, что снижает сложность поддержки пайплайна.

**Учитываемые trade-off’ы:**
- **Точность vs Интерпретируемость:** NN показала также лучший R² (0.893), но является «чёрным ящиком» и требует жёсткого контроля масштабов признаков. Для финансовой задачи объяснимость приоритетнее.
- ️ **Сложность пайплайна:** Отказ от логарифмирования таргета упрощает инференс (не нужно делать `exp()` обратно) и сохраняет предсказания в понятных бизнесу денежных единицах.

**Итог:** CatBoost выбран как оптимальное решение, удовлетворяющее требованиям к качеству, интерпретируемости и готовности к развёртыванию в сервисе кредитного скоринга.

## 7. Наблюдаемость, конфигурация и безопасность

### 1. Логи и наблюдаемость
- **Что логируется:**
  - **Запросы:** HTTP-метод, эндпоинт, входные параметры (без чувствительных данных), время начала обработки.
  - **Ответы:** HTTP-статус, время выполнения (latency), ID запроса (для трейсинга).
  - **Ошибки:** Полные трейсы исключений (stacktrace), статус-коды `4xx`/`5xx`, причины отказа (например, невалидные входные данные, падение модели).
  - **Важные события:** Успешная загрузка модели при старте сервиса, ротация моделей, аномалии во входных данных (если настроен мониторинг дрифта).
- **Как понять, что сервис работает корректно:**
  - Наличие живого `/health` или `/ready` эндпоинта, возвращающего `200 OK`.
  - Стабильные значения latency и отсутствие ростов `5xx` ошибок в логах.
  - Структурированные логи (JSON) легко парсятся и интегрируются с мониторингом (Prometheus/Grafana, ELK или аналоги), что позволяет строить дашборды по RPS, латентности и количеству ошибок.

### 2. Конфигурации
**какие параметры вынесены в конфиги (`configs/`, `.env.example`):**
- **Пути к артефактам:**
  - `MODEL_PATH` — путь к сериализованному файлу обученной модели (`CatBoost`).
  - `SCALER_PATH` — путь к объекту масштабирования данных (`StandardScaler`).
  - `CONFIG_PATH` — путь к JSON-файлу с конфигурацией эксперимента и гиперпараметрами.
- **Сетевые настройки:**
  -`APP_HOST` и `APP_PORT` — адрес и порт, на которых запускается API-сервер.
- **Настройки логирования:**
  - `LOG_LEVEL` — уровень детализации логов (например, `INFO` для продакшена или `DEBUG` для отладки).

**Что можно перенастроить без изменения кода:**
*   **Запуск новой версии модели:** Достаточно обучить новую модель, сохранить её в папку `artifacts/` и просто изменить значение `MODEL_PATH` в `.env` файле.
*   **Изменение окружения запуска:** Можно запустить сервис на локальном порту (например, `8000`) или в Docker-контейнере на другом порту (например, `5000`), изменив только переменную `APP_PORT`.
*   **Отладка:** При возникновении ошибок можно временно переключить `LOG_LEVEL` на `DEBUG`, чтобы увидеть больше информации в консоли, не пересобирая проект.

### 3. Безопасность
- **Избегание коммита секретов:**
  - Все секреты (токены, пароли, URI внешних сервисов, ключи MLflow) выносятся **только** в переменные окружения.
  - В репозитории присутствует `.env.example` с примерами заполнения, но **без реальных значений**.
  - Реальный `.env` добавлен в `.gitignore` согласно `SECURITY.md`. В `git` никогда не попадают токены, пароли или чувствительные данные.
- **Отсутствие чувствительных данных в репозитории:**
  - В репозитории нет персональных данных пользователей, API-ключей, токенов или паролей.
  - Датасет используется учебный/обезличенный (согласно правилам курса).
  - Секреты подставляются только на этапе запуска сервиса (через `dotenv` или переменные окружения в Docker/CI-CD). В `README.md` и `SECURITY.md` явно описан порядок работы с секретами и инструкция по настройке окружения.

## 8. Ограничения и дальнейшая работа

### Ограничения проекта
- **Данные:** Датасет содержит ~10 тыс. записей, является открытым и статичным. Отсутствуют временные метки, обратная связь по реальным решениям банка и сценарии концептуального дрейфа. Это ограничивает возможность валидации долгосрочной устойчивости модели.
- **Сервис и инфраструктура:** Реализован минимальный FastAPI без асинхронных воркеров, rate-limiting и авторизации. Метрики и логи собираются в памяти/локальных файлах, без централизованного мониторинга. 
- **Скорость и устойчивость:** Инференс занимает <50 мс на запрос, но сервис не тестировался под нагрузкой (>100 RPS). Нет fallback-сценариев (например, возврат бейзлайна или кэшированного ответа при падении CatBoost).

### Что можно улучшить при наличии большего времени

#### Улучшения модели
- **Ансамблирование / стэкинг:** Комбинация CatBoost, Random Forest и MLP для снижения дисперсии ошибок и улучшения R^2/RMSE.
- **Автоматический feature engineering:** Генерация взаимодействий признаков, отбор через permutation importance / SHAP, борьба с мультиколлинеарностью.
- **Интерпретируемость в проде:** Интеграция SHAP-значений в API-ответ для объяснения влияния каждого признака на лимит.

#### Улучшения сервиса
- **Продакшен-обёртка:** Переход на `gunicorn` + `uvicorn` с несколькими воркерами, добавление rate-limiting, JWT-авторизации и валидации входных схем через Pydantic v2.
- **Мониторинг и логи:** Интеграция Prometheus + Grafana для реальных метрик (latency, error rate, model drift), централизованные логи через Loki/ELK, алерты при аномалиях.
- **Кэширование и отказоустойчивость:** Redis-кэш для частых запросов, fallback на бейзлайн-модель при недоступности основной.

#### Улучшения данных и экспериментов
- **Автоматизация переобучения:** Пайплайн на Airflow/Prefect с триггерами по дрейфу данных (PSI/KS-тесты) и автоматическим запуском Optuna-тюнинга.
- **Сбор обратной связи:** Механизм логирования реальных решений банка и фактических лимитов для последующего fine-tuning и A/B-тестирования версий модели.
- **Расширение датасета:** Генерация синтетических данных с реалистичным шумом, добавление временных признаков или интеграция с внешними макроэкономическими индикаторами.
