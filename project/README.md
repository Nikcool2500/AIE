## 2. Структура проекта

Проект организован в следующей структуре:

- `requirements.txt` – зависимости проекта (библиотеки Python, необходимые для запуска).
- `report.md` – отчёт по проекту (постановка задачи, данные, эксперименты, результаты).
- `self-checklist.md` – чеклист самопроверки проекта перед сдачей.
- `notebooks/` – экспериментальные ноутбуки:
  - EDA, прототипы моделей, отдельные эксперименты.
- `src/` – основной код проекта:
  - модули для работы с данными;
  - обучение моделей;
  - запуск сервиса/скриптов.
- `data/` – демонстрационные/учебные данные:
  - **только открытые, синтетические или обезличенные данные;**
  - при необходимости – небольшие выборки для быстрого запуска.
- `configs/` – конфигурационные файлы:
  - `.env.example`
- `tests/` – тесты (юнит-тесты, простые проверки).
- `artifacts/` – сохранённые модели, отчёты, результаты экспериментов.

## 7. Ограничения и дальнейшая работа

В текущей версии сервис развёрнут в минимальной конфигурации: используется одна финальная модель (CatBoost), метрики и логи собираются локально (в памяти/файлах), а авторизация и ограничение частоты запросов не реализованы. Модель выдаёт точечный прогноз без оценки неопределённости, а пайплайн переобучения запускается вручную.

В дальнейшем проект можно развивать в следующих направлениях:
- **Мониторинг и MLOps:** интеграция Prometheus/Grafana для метрик, отслеживание дрейфа данных (PSI/KS-тесты) и автоматический триггер переобучения при деградации качества.
- **Оценка рисков:** добавление квантильной регрессии или conformal prediction для выдачи доверительных интервалов вместе с прогнозом лимита.
- **Безопасность и стабильность:** внедрение JWT-авторизации, rate-limiting, Redis-кэширования частых запросов и graceful degradation при недоступности модели.
- **CI/CD и версионирование:** настройка GitHub Actions для автотестов, сборки Docker-образа и деплоя, а также использование Model Registry для управления версиями моделей и A/B-тестирования.
